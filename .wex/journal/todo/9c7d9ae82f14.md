# Pages de repli : erreurs, démarrage, build des assets

Opened: 2026-10-16
Updated: 2026-10-16
Author: agent:main

## Contexte
Certaines pages s'affichent quand l'application ne peut pas se rendre elle-même. Elles ne peuvent donc utiliser ni le thème du DS ni aucun skin, et chacune a aujourd'hui son propre style, écrit à la main :
- `app-board/public/splash.php` : la page « Starting… » servie par `php -S` pendant que l'entrypoint installe les bundles montés. Fond sombre en dur, rafraîchissement toutes les 5 s, aucune information sur l'avancement.
- `symfony-loader/assets/system/fatal.html.twig` : « Assets missing », quand le build n'existe pas.
- Les erreurs 4xx/5xx : `symfony-loader/src/Controller/System/ErrorController.php` quand le kernel tourne. Quand il ne démarre pas du tout, il n'y a rien.

On veut un rendu commun, sobre et proche du DS, sans dépendre de lui à l'exécution.

## Pages visées
- Erreurs 400 / 403 / 404 / 500 / 503.
- Démarrage : une page générique, éventuellement complétée par une version propre à board. Si possible avec un suivi de l'avancement, même grossier.
- Build des assets en cours ou absent (loader).

## Avis (à valider)
- **Place : symfony-loader**, pas le DS. Le loader possède déjà la page « Assets missing » et l'`ErrorController`, et ces pages existent justement quand le DS ne peut pas servir. Board ne garde que ses étapes de démarrage.
- **Pré-générer le HTML plutôt qu'écrire une mini-app de repli.** Une commande (par exemple `loader:fallback:build`) rend les pages depuis des templates Twig au moment du build ou du release, en fichiers autonomes : CSS inline, aucun asset externe, clair/sombre via `prefers-color-scheme`. Ces fichiers sont servis par n'importe quoi : le serveur web quand le kernel ne démarre pas, `php -S` au démarrage, Symfony lui-même pour les erreurs. Le style tient dans un seul template, qui reprend à la main les quelques valeurs du DS en skin basic (couleurs, typographie, espacements).
- **Ne garder du PHP que pour le vivant.** Le suivi du démarrage demande un peu de dynamique : l'entrypoint écrit son étape dans un fichier JSON (`étape`, `total`, `libellé`), `splash.php` sert la page pré-générée plus ce JSON, et quelques lignes de JS l'interrogent puis rechargent la page une fois le démarrage fini. C'est le seul endroit où un repli en PHP se justifie, et il reste un seul fichier.
- **Kernel qui ne démarre pas** : déclarer le 500 pré-généré comme page d'erreur dans la configuration du serveur web (Caddy/FrankenPHP), puisque Symfony ne peut pas répondre.

## Reste à faire

- Template commun et commande de génération dans symfony-loader.
- Brancher `ErrorController`, la page « Assets missing », le `splash.php` de board et l'erreur au niveau du serveur.
- Fichier de progression écrit par l'entrypoint de board, et petit script de suivi.
